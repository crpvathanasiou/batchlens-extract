## Defect 1 — Prepare the reviewed HTML document exactly once per classification start

The current service calls `prepare_reviewed_document(...)` in `start_classification(...)`, then calls it again inside the background worker.

This violates the approved S4.2 boundary: prepare and validate the reviewed HTML once, then classify the already prepared pages.

Correct it so that:

- `start_classification(...)` prepares and validates the document exactly once.
- The already prepared `PreparedDocument` is passed in memory to the background worker.
- The worker must not receive the source path merely to call `prepare_reviewed_document(...)` again.
- The complete page fragments remain in memory only; they are never persisted.
- The expected reviewed-document binding remains verified during the one preparation.
- A changed file after preparation must not cause an unnoticed second interpretation of the document.
- Existing current-state progress/persistence behavior remains unchanged.

Add a focused service test that spies on or monkeypatches the service’s preparation boundary and proves one `start_classification(...)` causes exactly one complete document preparation, including after the worker finishes.

## Defect 2 — Validate persisted valid-response payloads with their fixed call schema

`PersistedCallOutcome.response` currently stores `dict[str, Any]`, but a persisted `availability="valid"` payload is not revalidated against the response schema selected by its fixed `call_id` during `CurrentClassificationState` validation/load.

This means malformed or wrong-group valid payloads can pass the store’s typed load contract.

Correct the persistence contract so that:

- A valid persisted call outcome is validated using the exact schema for its fixed call ID:
  - call 1 → `MaterialEquipmentResponse`
  - call 2 → `ProcessOperationsResponse`
  - call 3 → `DocumentSupportingResponse`
- The validation runs when persisted JSON enters the typed model, including `PageClassificationStore.load(...)` and `load_path(...)`.
- Empty responses remain attributable to their own call slots without union ambiguity.
- Existing valid persisted payloads from the runner continue to round-trip unchanged.
- A missing/invalid/wrong-group response payload for a `valid` outcome fails closed with a typed validation/store error.
- Non-valid outcomes continue to reject a response payload.
- Do not introduce a generic serialization framework or persist raw provider objects.

Add focused store tests that write persisted JSON with:

1. A call-2 `valid` response containing call-1-only `BILL_OF_MATERIALS`.
2. A `valid` response missing a required structured field.
3. A valid empty response for each call slot.

The first two must fail closed on load; the third must load and reconstruct/validate against the correct call schema.

## Defect 3 — A second service instance must not interrupt an active same-process worker

The local in-process active-worker guard is intended to enforce one worker per data directory. However, constructing a second `PageClassificationService` for the same data directory while the first instance is actively classifying currently runs startup interruption recovery and can mark the first instance’s truthful `running` state as `interrupted`.

Correct the concrete local behavior:

- If the data directory is currently in the existing in-process active-worker set, constructing another service instance for that same directory must not alter any running current state.
- Its `start_classification(...)` must still reject with `PageClassificationBusyError`.
- Startup recovery must still mark genuinely abandoned `running` states as `interrupted` when no active same-process worker owns that data directory.
- Do not introduce cross-process locking, a generic ownership framework, or a queue.
- Do not weaken the existing restart-recovery behavior.

Add a focused service test:

1. Start one service using the existing blocking fake runner.
2. While it is active, construct a second service for the same data directory.
3. Confirm the persisted state remains `running`, not `interrupted`.
4. Confirm the second service cannot start classification.
5. Release the first worker and confirm it completes normally.
