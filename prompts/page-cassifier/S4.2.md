## 1. Three locked calls per prepared page

Implement the async runner around the existing reusable boundary:

```python
app.llm.AsyncOpenAIWrapper.generate_structured(...)
```

For each page in a prepared S4.1 document:

- Use that page’s complete `page_html_fragment` as the user prompt.
- Use each matching locked prompt text as `system_prompt`.
- Use the matching S4.1 response schema:
  - call 1 → `MaterialEquipmentResponse`
  - call 2 → `ProcessOperationsResponse`
  - call 3 → `DocumentSupportingResponse`
- Call the wrapper exactly once per call slot.
- Do not supply `model_name`, `temperature`, timeout, retry count, or guardrails; the injected wrapper’s configured defaults remain authoritative.
- Do not create an OpenAI client or wrapper.
- Do not append prior pages, other call outputs, labels, or any hidden context.
- Do not use vision, PDFs, images, OCR, or another model path.

The three calls are independent. For this local MVP, execute them serially in fixed call order `1`, `2`, `3` for each page; do not pass one call’s output into another. Execute every remaining call even when an earlier call fails.

After the three outcomes for a page are available:

1. Use S4.1 `validate_call_response`, `failed_call`, and `missing_call` semantics as applicable.
2. Use S4.1 automatic source-evidence validation and merge rules.
3. Compute the S4.1 eligibility decision.
4. Persist that completed page result before moving to the next page.

A wrapper exception or unusable structured result becomes a truthful failed/invalid call outcome for that slot. It must not terminate classification of the other call slots or remaining pages. Do not leak API keys, raw provider payloads, or unbounded exception text into persisted state; store a concise safe reason only.

No extra retry system is authorized. The wrapper’s existing configured retry behavior is the only retry behavior.

## 2. Current-state-only persistence

Implement a small JSON store, specific to page classification.

Persist one current classification state per reviewed HTML identity at:

```text
<data-dir>/page-classifications/<stable-reviewed-html-identity-key>/current-classification.json
```

The directory key must be deterministic, filesystem-safe, and derived from the complete existing `ReviewedHtmlV1Input` binding, including its HTML-byte SHA-256. Do not use a source document ID alone, a page number, a random UUID, or a user-supplied path component.

Use a canonical, explicit serialization plus SHA-256 digest for this key. Keep this logic local to `store.py`; do not add a generic identity framework.

The current state must retain:

- The exact existing reviewed-document provenance and HTML-byte SHA-256.
- A fixed classifier/policy contract version identifier suitable for later provenance.
- Lifecycle status: `running`, `completed`, `failed`, or `interrupted`.
- UTC timestamps for creation, latest update, and terminal completion/interruption when applicable.
- Truthful progress: total page count, completed page count, and current page number when running.
- Completed per-page results in document/page order:
  - existing page binding;
  - all three call outcomes;
  - source-evidence validation results;
  - merged classification;
  - eligibility decision and reason.
- A concise safe terminal failure/interruption reason where applicable.

Do not persist raw HTML fragments, raw provider responses, secrets, request headers, prompt copies, retry history, classifier revision history, an approval record, or a generic job ledger.

The store must:

- Use atomic write semantics: temporary file in the target directory, flush, `fsync`, then replace.
- Validate JSON through the typed persistence contract on load.
- Fail closed on malformed/unknown persisted state; do not silently invent or repair data.
- Return `None` when no current state exists for the requested reviewed-document binding.
- Verify that loaded state matches the requested binding.
- Replace the previous `current-classification.json` only when a new explicit classification starts. There is no history or version browser.

A later explicit reclassification of the same reviewed HTML may replace the current state. It must never rewrite the classification snapshot that a later task will associate with a lexical run; that snapshot feature is not part of this task.

## 3. Small local service and truthful restart behavior

Implement a concrete `PageClassificationService`, not a generic queue, workflow engine, or execution framework.

The service must:

- Receive its data directory and an injected `AsyncOpenAIWrapper`.
- Receive the selected reviewed HTML path and expected reviewed-document binding when starting classification.
- Prepare and validate the document once using S4.1 before the worker starts.
- Create/replace the current state as `running`, then start one small local background worker.
- Classify pages one at a time, persist each completed page result, and persist truthful progress after each page.
- Expose a narrow read operation for the current persisted classification state.
- Reject a second start for the same data directory while this service’s classifier worker is active.
- Maintain one active classifier writer/worker per data directory within the local process, using only a small concrete guard in this service. Do not add cross-process locks, a shared execution module, or a generic ownership layer.
- Release the active-worker guard in `finally`, including unexpected failure.
- Mark the current state `completed` only after every page has a completed three-call/merge/eligibility result.
- Mark the current state `failed` if an unexpected worker-level error prevents completion, preserving already completed page results and truthful progress.
- On service construction/startup, find current classification files under its data directory that remain `running` from a prior process and mark them `interrupted` with a concise truthful reason. Do not auto-resume, auto-retry, or make new LLM calls after restart.

This task intentionally has no UI or API. Do not add a CLI merely to expose the service. A live configured-OpenAI manual run belongs to the later workspace integration task.

## 4. Persistence contracts

Add only the typed models/enums genuinely needed for the stored current state. Keep them separate from the locked LLM response schemas.

Required invariants:

- Every completed page result is derived from one `PreparedPageInput` and has the same immutable binding.
- Page results are in deterministic document order.
- A `completed` state has exactly one completed result for every prepared page and no running page.
- A `running`, `failed`, or `interrupted` state never claims all pages completed unless they actually are.
- The persisted three outcomes remain attributable to their fixed call IDs after JSON round-trip.
- Do not rely on ambiguous union deserialization for empty call responses. If the existing `CallOutcome.response` union cannot faithfully round-trip the schema-specific response for all three call slots, add the smallest explicit local persistence representation and reconstruct/validate using the fixed call ID. Prove it with tests.
- No page is excluded merely because a call failed, was invalid, was incomplete, returned `needs_review`, conflicted, or had unverified source evidence. Continue to delegate this decision to S4.1 rules.
