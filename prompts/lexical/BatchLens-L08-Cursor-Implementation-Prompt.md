## Deliverable

Create one focused aggregation module (for example `src/app/lexical_extraction/dictionary_aggregation.py`) with a narrow synchronous interface over an L07 raw-discovery iterator, its replayable block source, a validated open L04 `KnowledgeSnapshot`, and finite L02 resource limits. Produce an iterator of L01 `BlockRecord` values in physical page/block order; preserve blocks with zero dictionary matches. It may expose a small aggregate count/coverage result **only after complete consumption**. Do not construct a whole-run tree, final run outcome, or published artifact.

Use a run-local, automatically cleaned **temporary disk spool/sort** (SQLite or an equally simple bounded approach) to regroup shard-order discoveries by block ID, original span, and source-reference identity. This spool is execution scratch, not a persistent knowledge catalogue, and must never write the L04 snapshot. Keep memory bounded by explicit finite buffers and per-block/group limits; if one pathological block or candidate collision cannot fit, raise a safe structured resource error and leave no claim of completed aggregation. Do not use a global in-memory set of all matches, blocks, or source references; do not silently truncate. Close/delete scratch data on normal completion, early iterator close, or failure. Treat disk/write errors explicitly.

Aggregate all **dictionary components** (`unit_operations`, `process_steps`, `materials`, `equipment`, `parameter_names`) as follows:

- One document occurrence per `(block, original start/end, matched_text)` for dictionary hits. Keep different spans and valid overlaps, including `granulation` alongside `wet granulation`; keep repeated spans at different offsets. Combine distinct component applicability. A repeated flat row is **not** a second document mention. Preserve distinct catalogue/lexical interpretations as separate candidates at that span, including FDA/EMA versus ChEBI, different lexical-term IDs, alias qualifications, policies/roles, and equipment-scoped parameter IDs. Do not use display-name equality alone as a grouping key.
- Rehydrate candidate metadata via **single-table L04 lookup** and the L05 fixed mapping, with at most a finite small source-row cache if useful. Require that retrieved table/row, mapped source field, original literal, role/component and snapshot identity agree with the raw discovery; absent/mismatched rows are explicit failures, never an empty candidate list or fallback to CSV/another snapshot. Carry only the L01 fields: native IDs in separate namespaces, display name, alias type/source qualifiers, UO policy/role, process-step support reference, and catalogue equipment scope as appropriate. Never infer an installed asset or attach a parameter to a document equipment mention. Preserve generic cues without inventing `Operation ID` and independently eligible steps even when the UO search field was inactive.
- Deduplicate a repeated discovery of the **same source reference** at the same span, retaining `exact` before `normalized_exact` when both are valid. Then group **different source `row_id`s only when their mapped candidate interpretation is identical**: same source table/field, component/role, original dictionary spelling, native identity namespace and value (including absence), lexical-term ID (including absence), display name, alias qualification, policy/record type, relation/operation role, and every other L01 candidate qualifier/provenance value apart from `row_id` and match-method priority. A difference in any selected candidate field means separate candidates. Never merge distinct names, terms, fields, roles, source catalogues, step IDs, parameter scopes, or differing source evidence; never infer that equal names identify one entity. This rule may collapse repeated flat rows for a UO whose only difference is an unrelated linked process step, but it must not suppress a separately matched process-step label or import unmentioned steps. Apply the same rule to materials and equipment; do not add catalogue-specific grouping engines.
- For each such group, use one deterministic representative `row_id` plus the other actual matching `row_id`s as **supporting references**, with unique stable ordering and no invented IDs. The representative remains in the existing L01 `row_id` field; add only a small backward-compatible `supporting_row_ids` tuple to the shared L01 candidate base (default empty, excluding the representative), with a validator for duplicate/representative IDs. Keep the real source rows available for later audit/semantic retrieval by their IDs. Do not copy the full source rows, process-step prose, or relationship columns into the result. No lookup of other rows merely because they share an operation/equipment/material identity.
- Construct the appropriate L01 candidate types and `ExactEvidence`/`NormalizedExactEvidence`, then an L01 `DictionaryOccurrence` with deterministic `occurrence_id` and canonical candidate order independent of shard size and raw emission order. Grouped evidence uses the strongest valid method; an `exact` method requires candidate `matched_term == location.matched_text`. Validate each emitted `BlockRecord` against its original block using the L01 boundary. An unresolved or `context_required` candidate remains evidence, not an extraction failure or a claim of execution.
- Replay blocks to emit document order and verify that the finalized HTML identity remains the same as L07's complete passes; do not mix revisions. Final completion is unavailable until the raw iterator and the final block replay have both finished successfully. Previously yielded records before a late failure are provisional and must not be presented as a published complete result. Keep page and block ordering from L03; final `PageRecord`/run serialization is later work.

This is an **internal evidence/result contract**, not a review-screen design. A later review/result projection should show the matched document text, location, concise candidate label/identity and ambiguity for editing/approval; keep the detailed `row_id` provenance accessible when needed, without displaying every repeated flat row as a separate finding. Do not build that projection or change the existing review UI in L08. Do not declare a candidate uniquely confirmed just because identical flat rows were grouped.

The L01 `UnitOccurrence` has a different evidence/provenance shape. If `units` raw discoveries are passed to this dictionary-only aggregator, reject them clearly instead of dropping or falsely attaching them to equipment parameters. Material quantity expressions, equipment parameter values, and any unit vocabulary beyond L05 Equipment.Unit remain later tasks.
