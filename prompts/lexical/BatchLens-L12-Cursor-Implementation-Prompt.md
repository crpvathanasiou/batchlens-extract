## Deliverable: one callable run boundary

Add a small `lexical_extraction/runner.py` and, only if needed for clarity, a focused monitoring helper. Accept an L02 `EffectiveExecutionConfiguration` (a thin config-path convenience entry point is optional) and a **bounded caller-owned evidence sink** suitable for the later L13 publisher. Return a typed run summary with validated input identity when available, L04 knowledge identity when validated, L01 `RunProvenance` when all required identities are known, L01 `ExtractionOutcomeRecord`, and compact measured monitoring data. Specify the callable signature and the sink's minimal begin/write/complete-or-abort lifecycle. Stream page/block evidence to the sink; do not assemble a whole document, vocabulary, or result tree in memory. The sink must distinguish provisional data from a completed component. L13 will persist/publish it; test doubles may retain a **small synthetic fixture** in memory.

Validate the reviewed HTML v1 fully to obtain its exact-byte SHA-256 and mandatory producer metadata, and preflight the read-only flat SQLite snapshot **once per run**, before search. Preserve the same identities through all replay passes; a changed/incomplete HTML or snapshot fails affected work without claiming completed coverage. A failure before successful HTML validation uses `PreValidationFailure` or an equivalent honest error boundary and never fabricates job/revision/generation/hash. Config, HTML, or snapshot preflight failures stop search with structured errors; no CSV fallback, rebuild, or conversion-HTML substitution. Close the snapshot and all streams on success, failure, and early stop.

Execute exactly L02's resolved component union and pass its sole matching switch `fuzzy_enabled` to dictionary/parameter-name search. Materials, UNII, and units remain non-fuzzy, even when fuzzy is ON. Use the existing L05→L07→L08 path for `unit_operations`, `process_steps`, `materials`, and `equipment`; use the existing L10 composition for `parameter_names`, `units`, `quantity_expressions`, and `parameter_value_expressions`. Do not run `parameter_names` through both paths or duplicate a value when both value components are selected. Reuse the same L03/L04 reader and matching core, with simple per-component execution where that makes failure isolation and bounded output easier. `_with_` presets mean co-execution only; a mention has no inferred UO/material/equipment relationship or mandatory child data.

Emit ordered page/block evidence, including empty blocks/pages where the input contract provides them, exact original offsets and source references. Preserve overlaps, repeated occurrences, ambiguous candidates, and `supporting_row_ids`. Keep the component selection visible on each occurrence. A zero-hit requested component is **completed with count 0** only after its full stream/replay succeeds. A failed shard or incomplete child stream cannot be counted as completed. Completed independent components remain usable if another component fails; overall outcome is `partial` with explicit failed component and safe error. If a shared prerequisite fails, mark all affected requested components failed and keep unavailable identities/measurements absent. Do not silently treat provisional events as completed output. Choose the smallest coherent grouping of shared stages; document which components share a failure boundary. There are eight independent components and seven combinable presets already defined by L02; do not reimplement preset resolution.

Populate `RunProvenance` from real validated input/snapshot identity, effective configuration SHA-256, requested presets/components, resolved components, fuzzy selection, engine/dependency versions, and a **reproducible digest of the fixed V1 rules actually used** (`rules_sha256`, not the synthetic fixture digest). Keep rule identity simple and explicit; no user-selectable policy file or configurable search framework. Generate run IDs and time measurements honestly; content/order apart from run identity/timestamps must be deterministic for pinned inputs. Separate extraction outcomes from publication: L12 must not construct a `PublicationRecord` with a completed final-manifest claim or write a final manifest.

## Operational monitoring and bounded execution

Provide a compact in-memory monitoring summary for L13 to persist: observed pages and blocks, completed/failed/zero-result components, matches by component and method where observable, eligible terms/rows/shards/candidate counts where accurately measurable, stage elapsed times, and configured resource limits. Mark unavailable phase splits/counters as unavailable or omit them; never print guessed zeroes. Include measured **peak process memory** and method/platform when a supported nonprivileged measurement is available; otherwise report unavailable. Do not inspect physical RAM to choose shard sizes, adapt limits to hardware, require elevated access, or inherit L09's 32 GiB benchmark budget as a runtime default. Keep logging structured and small using application conventions: run ID, safe stage/component, status, counts, elapsed time, and error code; do not log full document text, catalogue rows, credentials, or unrestricted paths. No dashboard, telemetry server, audit ledger, or new dependency merely for monitoring.

Keep exceptions bounded and map known L02–L11 errors to L01 `SafeStructuredError` without leaking sensitive path/text in messages or logs. A failed sink write is an execution/output failure, not a completed extraction. L13 owns atomic file publication and the final manifest; a successful L12 stream is not itself a published result. Use the existing finite L02 limits and accepted stream cleanup behavior; no unbounded document buffering or repeated snapshot preflight per component. Minimal compatible seams in accepted modules are allowed **only when necessary** for trustworthy counts or orchestration; explain each such change and protect it with a regression.
