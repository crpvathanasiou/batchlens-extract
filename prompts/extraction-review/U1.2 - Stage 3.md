# U1.2 — Simple file-based Save, Approve, and revision snapshots

Implement **U1.2 only** for **Stage 3 — Extraction Review Workspace**.

U1.1-R3 contracts and pure transitions are accepted and remain unchanged. This task adds simple local persistence for one document/run review result.

## Product decision

Do **not** use SQLite, a database, indexes, background recovery machinery, worker locking, or a generic storage framework.

A document’s extraction findings are small enough to keep as ordinary JSON. This remains true for approximately 500 or 1,000 findings.

The reviewed HTML and raw Stage 2/L13 artifacts remain read-only. Stage 3 stores only the user’s review result: current findings, edits, revisions, and final approval.

## Scope

Create a small local file store and service for:

1. Creating a review from an initial full finding list.
2. Saving edits.
3. Approving the currently saved result.
4. Reloading the current result after restart.
5. Keeping previous saved revisions as optional version history.

Do not implement document selection, L13 import, extraction execution, evidence lookup, API routes, UI, workers, graph relationships, LLM work, or associations.

## Local JSON layout

Use a caller-supplied data directory. Use a deterministic safe workspace directory derived from the immutable source/run binding; do not use untrusted path text directly.

Use a simple layout such as:

```text
<data-dir>/
  extraction-reviews/
    <workspace-id>/
      current-review.json
      revisions/
        <revision-id>.json
      approvals/
        <transition-id>.json
```

### Revision snapshot

Each file in `revisions/` is immutable and contains the complete review snapshot for one saved content revision:

- U1.1 source/run binding and revision metadata.
- Full current finding list for that revision.
- User-added, changed, and removed finding provenance already represented by the locked U1.1 contracts.
- No active approval embedded into the content revision.

A full JSON snapshot is intentional. Do not optimize it into deltas, tables, or indexes in this task.

### Current-review file

`current-review.json` is a small mutable pointer/view of the currently presented result. It identifies:

- The current saved revision.
- The current full finding list, or a reference to the identical current revision snapshot.
- The current final approval record when the current revision is approved.

Use the simplest representation that avoids duplicate or contradictory content. Prefer referencing the immutable current revision snapshot if that keeps the design clearer.

### Approval record

Each file in `approvals/` is immutable and contains the locked `ExtractionResultApproval` record.

It names:

- actor,
- server timestamp,
- exact approved revision ID,
- source/run provenance already required by U1.1.

Approval never changes a revision snapshot or the HTML.

## Save and approval behavior

Use atomic JSON publication: write a complete temporary JSON file in the target directory, flush it, then atomically replace the final path.

### Create review

Accept:

- A valid U1.1 initialization command.
- The initial complete finding list produced by the future import layer.

Persist the first immutable revision snapshot and `current-review.json`.

U1.2 does not create, import, verify, or modify raw Stage 2 artifacts. It only stores the supplied findings and their existing provenance.

### Save

When the user saves:

- Load the current review snapshot.
- Check `expected_revision_id`.
- Use the locked U1.1 transition rules for the bounded edit batch.
- Apply the resulting edits to the in-memory full finding list.
- Write one new immutable full revision snapshot.
- Atomically update `current-review.json` to the new unapproved revision.

A no-op save writes nothing and retains approval status.

A stale save returns a conflict and writes nothing.

### Approve extraction result

When the user approves:

- The target must equal the currently saved revision ID.
- Unsaved edits cannot be included.
- Write one immutable approval record.
- Atomically update `current-review.json` so that it shows the current result as approved.

A later Save writes a new revision and clears only the active approval in `current-review.json`. Previous revision and approval files remain unchanged.

### Simple retry behavior

Keep retry behavior proportionate:

- If the immediately current saved revision or approval already carries the same operation identity and matching request data, return that committed result without writing another file.
- If the operation identity is reused with different request data, return validation error.
- A stale operation after a later revision may return conflict; do not scan all historical files merely to implement old-operation replay.

## Version history

Provide a small local `list_versions()` or equivalent service method.

It may read the revision filenames and compact revision metadata directly because this is a small local review workspace. It does not need a database, index, pagination system, rebuild mechanism, or audit framework.

The service must never modify old revision or approval files.

## Required tests

Add meaningful local-file tests for:

1. Create a review with a full finding list; reload it after a new service instance starts.
2. Save an edit; verify the new revision snapshot contains the full updated finding list and the earlier snapshot bytes remain unchanged.
3. Approve the saved result; verify a separate approval file names the exact saved revision and does not alter that revision file.
4. Save after approval; verify the new current revision is unapproved and the earlier revision/approval files remain available.
5. No-op save writes no new revision.
6. Stale save and stale approval write nothing.
7. Matching immediate retry does not create duplicate revision or approval files; operation-ID reuse with different data is rejected.
8. A review with 1,000 findings saves and reloads correctly.
9. Findings with `no_document_evidence`, including page-assigned findings without an exact span, save and approve correctly.
10. Read-only source/run references remain unchanged.
