## 1. Make committed review revisions immutable

The current approval transition replaces a saved revision with a new Python object that has the same `revision_id` and an added `result_approval`. This is not acceptable.

A saved extraction-review revision is immutable once committed. Its content, provenance, and revision ID must never be altered by approval.

Implement the smallest clear structure that satisfies this:

- `ExtractionReviewRevision` represents one immutable committed content revision.
- `ExtractionResultApproval` is a separate immutable approval record/event.
- The approval record names the exact committed `approved_revision_id`.
- Current status is derived from the current head revision and a separate approval record that targets it.
- Approval must not rewrite, replace, or enrich the approved content revision.
- A content save creates a new revision and clears the current approval pointer/status for that new head.
- The previous revision and its separate approval record remain historical.
- Repeating approval of the same current saved revision is an unchanged result. It must not create a duplicate approval record.

Keep the model concrete. Do not create generic event, workflow, approval-scope, or lifecycle abstractions.

`transition_id` may remain the identity of the immutable approval record and `operation_id` may remain the safe-retry identity. Their roles must be documented clearly and they must not be confused with `approved_revision_id`.

## 2. Remove whole-history and whole-result state from U1.1 contracts

The current `ExtractionReviewWorkspaceState` stores every revision in a tuple, and every save appends to and copies that entire tuple. Each revision also stores the full finding collection.

This violates the accepted bounded-revision direction and would force future storage/API work to load whole history and whole extraction results.

Replace this shape with a bounded current transition context:

- Do not retain a tuple/list of all historical revisions in the state model.
- Do not retain a tuple/list of all historical approvals in the state model.
- Do not copy the full Stage 2 finding result into every saved review revision.
- Do not retain an ever-growing `edits` history inside each finding.

Persistable review revisions must carry only a bounded delta for that revision:

- The initialization revision records immutable source/run/raw-result references.
- A save revision records its parent revision ID and a bounded normalized change set.
- A change set is limited by `MAX_FINDING_EDITS_PER_SAVE`.
- User-added finding data is stored in the add delta.
- Change/remove deltas identify the affected finding and preserve their actor, server-supplied timestamp, and required prior/current values.
- History is later derived from committed revisions and approval records. It is not embedded in every current finding.

For pure transition testing, introduce an explicitly named bounded input context for the current head, current content revision, current approval if any, and only the resolved findings addressed by the requested edit batch. This context is transient; it is neither persisted history nor a complete extraction result.

The save transition must emit the one new immutable revision delta and updated current head/snapshot. The approval transition must emit the one immutable approval record and updated status/snapshot. It must not require a whole-history or whole-artifact load.

A revision fingerprint, if retained, must be based on the bounded revision material and its parent/binding identity. Do not calculate it by serializing an entire historical result.

## 3. Correct finding origin, evidence, and edit semantics

### Origin and evidence

Preserve the distinction between lexical findings and user-added findings:

- A finding imported from Stage 2 remains source-labelled `lexical`, even after a user correction.
- A user-added finding must be explicitly identified as user-added. It must not be represented as a fabricated lexical occurrence such as `occurrence_id="user-added"`.
- Do not invent page, node, span, occurrence, candidate, or catalogue references.
- A finding with no document evidence must be explicitly `no_document_evidence`.
- A finding with `no_document_evidence` cannot carry fabricated page/node/span evidence.
- A finding with document evidence must contain valid supplied source evidence.
- Findings with real source evidence but no assigned page remain valid unassigned findings. They remain part of final approval.

Use a small explicit origin field or equivalent discriminated structure. Do not introduce a finding approval/rejection lifecycle.

### Add provenance

The add command must carry user-entered finding content, not prebuilt client-controlled audit provenance.

The pure transition must create `added_by_user` provenance from the command’s actor and server-supplied timestamp, just as it creates `changed_by_user` and `removed_by_user` provenance. Do not trust a nested client-provided actor or timestamp as committed provenance.

### Change semantics

The current change command silently clears `page_number` because its default is `None`.

Replace this with a simple non-ambiguous shape:

- A change command must carry the complete desired current user-facing finding value, including component, display text, page assignment, and evidence state; or use another equally explicit representation that distinguishes “unchanged” from “set to null”.
- A text-only edit must preserve the existing page assignment and evidence state.
- An explicit unassignment must be possible and remain distinct from an omitted field.
- Preserve immutable original lexical evidence when correcting a finding.
- Support correction of the user-facing component as well as text and assignment when needed.
- Reject duplicate targets within one bounded edit batch unless there is a documented deterministic reason to allow them.

## 4. Strengthen essential identity and integrity validation

Add focused validation for:

- `DocumentSourceReference.job_id` matching the reviewed HTML job ID.
- Unique finding IDs in relevant bounded inputs.
- Unique revision identities and valid parent linkage in the local transition context.
- Approval identity matching the exact target content revision and that revision’s job, run, document hash, and HTML-byte SHA-256.
- No approval record being treated as applicable to a different current revision.
- No evidence-less finding being accepted with the default `document_evidence` state.
- No fabricated lexical origin/evidence for a user-added finding.

Keep `document_hash` and reviewed HTML byte SHA-256 as distinct fields with distinct semantics. Constructing contracts still does not verify files or hashes on disk.
