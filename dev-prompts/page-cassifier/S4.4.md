## Implement only this vertical local slice

### 1. Local API and coordination boundary

Add the smallest focused local Stage 4 adapter needed by the existing extraction-review HTTP surface. It may be a small addition to the existing workspace/API modules or one narrowly named local adapter module; do not create generic workflow, queue, or execution infrastructure.

Use the existing approved-document registry and identity binding. A document is identified only by its existing approved `job_id`, `review_revision_id`, reviewed-HTML v1 provenance, and page numbers. Do not introduce any PDF identity or new page identity.

Provide narrow local API support for:

- listing selectable approved/reviewed documents;
- reading the current classification state for a selected approved document, if present;
- starting `PageClassificationService.start_classification(...)` for that exact selected reviewed HTML binding;
- returning truthful classification progress and terminal status after reload;
- returning the reviewed page HTML for the selected approved document before extraction;
- submitting the existing `LocalLexicalJobService.submit_classified_full_extraction(...)` action;
- returning either:
  - a submitted lexical local-job identifier/status, or
  - the existing non-error `no_eligible_pages` result and its exact message;
- reading truthful queued/running/completed/failed/interrupted status for that submitted local lexical job so the UI can distinguish lexical processing/publication from classification.

Keep the existing Stage 3 review endpoints and their request/response behavior intact.

Use safe bounded local error responses. Do not leak filesystem paths, API keys, raw exceptions, prompts, or model responses.

At the local harness composition boundary, reuse the existing configured settings, OpenAI provider, and `AsyncOpenAIWrapper` exactly as they already exist. Do not modify files under `src/app/llm/` or `src/app/settings.py`, create another client/wrapper, override model/timeout/retry/temperature, or make a real request in tests.

### 2. Classification and run-context truthfulness

The API/UI view model must expose only truthful classifier information required by the user:

- document/page number;
- current classification status, progress, timestamps, and safe terminal reason where applicable;
- per-page final/provisional labels;
- each returned evidence item (`label`, `quote`, `reason`, `element_id`);
- source-evidence validation/merge state, including `needs_review`;
- eligibility decision and reason.

Do not add classifier approval, label editing, retry controls, history, revisions, or a classifier-management screen.

A `needs_review`, incomplete, invalid, conflicting, failed, or interrupted classifier outcome remains visible and does not block **Extract All** once the classification state is terminal. It must never be displayed as approved.

For a classified lexical job, load classification display data from that job’s immutable S4.3 `classification.json` snapshot, not from a later current classification. Validate the snapshot’s digest and reviewed-HTML binding against the job before returning it. A later reclassification must not change the labels displayed with an earlier classified run.

For a legacy/unclassified lexical job, do not invent a classifier context.

### 3. Existing Vue extraction-review workspace

Extend `frontend/src/components/ExtractionReviewWorkspace.vue` and `frontend/src/extractionReview.ts`; do not create a disconnected second page or application.

Required local UI behavior:

- show selectable approved/reviewed documents before extraction;
- keep approved HTML on the left;
- show selected-page classification labels, evidence, validation/merge state, and eligibility/exclusion result on the right;
- provide exactly one classifier action: **Classify pages**;
- while classification is running, show truthful page progress/status and disable conflicting local actions;
- after a terminal classification state, do not present a classifier retry/reclassification control;
- make **Extract All** available only when a terminal current classification exists; it must call the classified S4.3 path and always means Stage 2 `full`;
- do not block **Extract All** merely because a page is `needs_review`, incomplete, invalid, conflicting, or failed/interrupted;
- show the explicit non-error no-eligible-pages message without creating or pretending that an extraction run exists;
- after lexical submission, show truthful queued/running/publishing/completed/failed/interrupted lexical status separately from classification status;
- when the lexical job completes, open that job in the existing extraction-review workspace and show its lexical findings together with its immutable classification snapshot;
- retain existing By page editing, All findings read-only navigation, Add/Edit/Remove/Restore/Save/Download TXT, category legend, and the one final **Approve extraction result** action unchanged;
- make clear that classification labels are informational and do not change the meaning of Stage 3 final approval.

Use a small fixed local polling interval only while classification or the submitted lexical job is non-terminal. Clear polling on unmount, document/job change, terminal status, and request failure. Do not add websockets, a general polling framework, a queue UI, or a lexical-action selector.
