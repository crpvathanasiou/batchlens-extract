## 2. Prepare the document once, then select prepared pages

Implement a small synchronous preparation boundary and pure page derivation/lookup helpers.

**Prepare and validate one complete reviewed-HTML document once. Do not parse, hash, or validate the entire document again for each selected page.**

The preparation boundary must:

- Consume the complete reviewed HTML through the existing reviewed-HTML v1 validation path.
- Complete that validation before returning a prepared document.
- Verify the expected reviewed-document provenance and original HTML-byte SHA-256 once.
- Reuse `ReviewedHtmlV1Input` rather than inventing another document identity.
- Derive all page inputs from the same validated document content.
- Return a deterministic prepared-document object whose pages retain their existing page numbers and HTML page identifiers.

Use the existing reader’s public validation boundary unchanged. Any read-only input adaptation required by that boundary belongs in `page_input.py`; it must not introduce storage, temporary persisted results, or a new validation framework. Keep content transformations and page lookup pure.

The existing reader finalizes its identity only after complete consumption. An early page yield must never be treated as a finalized document identity.

Each prepared page must expose:

- The same finalized reviewed-document provenance.
- Its existing page number and HTML page identifier.
- Its complete original HTML fragment, including the enclosing page section, attributes, tables, and descendants.
- Readable page text.
- A mapping of actual page-local HTML `id` values to their contained readable text.

Future code must be able to select a prepared page by its existing page number without rereading, reparsing, rehashing, or revalidating the whole document.

Invariants:

- Use the existing `section.page`/`data-page` boundary. Do not derive identity from a PDF, array position, generated UUID, or classifier response.
- Reject a mismatched document binding, absent requested page, ambiguous page identity, or ambiguous duplicate HTML ID explicitly.
- Ensure validation and page-fragment derivation refer to the same document bytes; do not combine provenance from one read with unchecked content from another.
- Do not duplicate approved-document eligibility checks.
- Preserve complete original page fragments. Do not reconstruct them from lexical `BlockRecord` text, truncate them, summarize them, or append neighboring pages.
- Root provenance remains in the application contract; do not inject invented identifiers into page HTML.
- Readable-text extraction excludes scripts, styles, and comments, while the original page fragment preserves them.
- Preserve meaningful text order and inline continuity; use readable separators for block boundaries, line breaks, and adjacent table cells.
- Actual HTML `id` is distinct from `data-node-id`, `data-element-id`, and OCR references. Never substitute those attributes for an absent HTML ID.
- Element text includes readable descendants and follows the same extraction rules as page text.
- Do not silently overwrite duplicate IDs.
- Do not implement CSS rendering, OCR, image interpretation, or lexical filtering.

Keep this foundation independent of Stage 2 matching. Existing contracts may be reused through public imports; do not modify Stage 2 or depend on its private parser internals.

## 3. Call outcomes and structural validation

Represent the three fixed call slots explicitly. No generic execution framework is needed.

The pure validation boundary accepts supplied response payloads or explicit missing/failed outcomes. Validate each supplied response with its matching Pydantic model, including revalidation of already-constructed model instances.

Keep these concepts distinct:

- Call availability/structural validity: valid, missing, failed, invalid.
- A structurally valid response’s original assessment status.
- Source-evidence verification.
- Merged page status and reasons.
- Extraction eligibility and reason.

Malformed JSON, wrong-group labels, missing fields, missing required evidence, evidence/label misalignment, and other schema violations make the call **invalid**. A refusal or supplied failure is unsuccessful, not an `empty` response.

Do not parse out apparently usable labels from a structurally invalid response and promote them to validated findings. Preserve valid/provisional findings from the other calls. Do not repair invalid responses.

Keep outputs typed, deterministic, and explicit enough to retain all three call outcomes and explain merge/eligibility decisions. Do not add job states, timestamps, retry records, provider objects, storage schemas, or approval fields.

## 4. Automatic source-evidence validation

For every structurally valid evidence item:

1. Normalize source text and quote using **HTML-entity decoding and whitespace collapsing only**.
2. Require a nonempty normalized quote to occur as a contiguous substring of the normalized readable page text.
3. If `element_id` is non-null, require that exact ID on the selected page and require the quote within that element’s normalized readable content.
4. If `element_id` is null, page-level quote matching is sufficient.

Use the prepared page’s readable text and ID mapping. Do not reparse the complete document during evidence validation.

Decode consistently with the HTML parser; avoid accidental repeated entity decoding. Do not case-fold, apply Unicode normalization, fuzzy-match, correct OCR, translate, paraphrase, splice distant passages, or invent IDs.

Distinguish:

- Missing `element_id` **field**: structural invalidity.
- Explicit `element_id: null`: structurally allowed.
- Non-null ID absent from the page, present only on another page, or not containing the quote: source-validation failure.
- Ambiguous duplicate HTML ID: explicit page-input preparation error, never verified evidence.

Source-validation failure must:

- Preserve the returned label, quote, reason, and ID unchanged.
- Mark the affected evidence unverified with an explicit reason.
- Mark the page as requiring review.
- Prevent exclusion.

It must not invalidate otherwise valid response structure, silently drop a label, fabricate replacement evidence, or change the response’s original status.

If another call is missing/failed/invalid, the page remains **incomplete**, while its evidence-validation failures and review requirement remain explicit. Do not let one status erase the other condition.

A matching quote verifies source support only. It does not prove semantic classification accuracy or label completeness.

## 5. Locked merge behavior

Merge only the three expected call outcomes for the same page/input binding. Reject mismatched bindings rather than merging different pages or document revisions.

Preserve deterministic order: call 1, call 2, call 3, then each prompt’s label order. Preserve each label’s evidence and originating call. Do not vote, cancel labels, introduce a fourth call, or select one dominant page type.

Apply these rules:

| Condition | Result |
|---|---|
| Any call missing, failed, or structurally invalid | Incomplete; retain findings from valid calls as provisional; no completed classification, fallback, or exclusion. |
| All calls valid and any response `needs_review` | Retain the label union; page requires review; no fallback. |
| All three responses `empty` | Empty labels and empty page result; no fallback. |
| Valid responses disagree between `empty` and `ok` | Retain the union; record the status conflict; page requires review; no fallback. |
| All three responses `ok`, union nonempty | Completed label union, subject to source-validation review flags. |
| All three responses `ok`, union empty | Application-generated `OTHER_UNCLASSIFIED`; page requires review. |

Source-evidence failures additionally require review and prohibit exclusion, as specified above.

`OTHER_UNCLASSIFIED` must have explicit application-generated provenance and the fallback reason. It has no fabricated LLM evidence. Never assign it for incomplete calls, all-empty responses, a status conflict, or merely because part of a labeled page remains unclassified.

## 6. Conservative eligibility rule

Implement the exclusion policy separately from classification merge semantics, within the small pure rules module.

The authoritative fixed exclusion set for S4.1 is exactly:

- `NON_RELATED`
- `COVER_PAGE`
- `TABLE_OF_CONTENTS`
- `DOCUMENTATION_INSTRUCTIONS`
- `REFERENCE_DOCUMENTATION`
- `SIGNATURE_LOG`
- `SIGNATURE_APPROVAL`
- `ACKNOWLEDGEMENT`
- `BATCH_REVIEW_DISPOSITION`
- `DOCUMENT_CHANGE_HISTORY`

Exclude only if:

- All three calls are present and structurally valid.
- There is no failed, incomplete, conflicting, `needs_review`, or source-unverified outcome.
- The final label set is nonempty.
- Every final label belongs to that set.

Every other page remains eligible. Return an explicit eligibility decision and deterministic reason.

Required examples:

- `TABLE_OF_CONTENTS` only, otherwise fully valid → excluded.
- `COVER_PAGE` + `BILL_OF_MATERIALS` → eligible.
- `SIGNATURE_APPROVAL` + `PROCESS_EXECUTION_RECORD` → eligible.
- Empty, fallback, incomplete, conflicting, or source-unverified result → eligible.

Do not feed this policy into the prompts or response schemas. Do not implement Stage 2 routing or an allow-list in this task.
