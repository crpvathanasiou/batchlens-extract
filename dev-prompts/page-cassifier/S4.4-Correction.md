## 1. Correct approved-document switching in the Vue workspace

In `frontend/src/components/ExtractionReviewWorkspace.vue`, selecting a different approved document while an extraction review is open currently leaves the old `review` object active. Consequently, page navigation and HTML loading continue to use the old lexical job, while the approved-document picker displays a different document.

Correct this so the approved-document picker always has one truthful context:

- If the user selects a different approved document, switch out of the currently open lexical-review context before loading the newly selected document’s pages, classification, and HTML.
- Do not display the previous job’s findings or immutable classification snapshot for the newly selected document.
- Ensure the left HTML pane uses the newly selected approved document before extraction.
- Preserve the existing extraction-run selector behavior: selecting a completed run must still open that run and its immutable classifier snapshot.
- Do not silently discard unsaved Stage 3 edits. While an extraction review has unsaved edits, prevent switching to a different approved document and show a clear local message that the user must save before switching. The existing review, drafts, approval state, and selected run must remain intact.
- Clear only the now-inapplicable review/job/classification transient state after a safe document switch.
- Keep one final action only: **Approve extraction result**.

Add focused frontend tests for:

- selecting a different approved document after opening a lexical run shows the new document’s HTML/classification and no prior run findings;
- attempting that switch with unsaved edits leaves the current review and drafts intact;
- selecting a completed run still restores its matching immutable snapshot and lexical findings.

## 2. Make classified-snapshot validation happen before Stage 3 mutations

In `src/app/api/extraction_reviews.py`, the optional classified snapshot is currently assembled while building the response after `save_review(...)` or `approve_saved_result(...)`. If the immutable snapshot is missing, malformed, has a digest mismatch, or has a binding mismatch, the Stage 3 mutation may already be committed while the HTTP response becomes an error.

Correct this transactional ordering:

- For a classified job, load and validate the immutable classification snapshot through the existing Stage 4 adapter before calling `save_review(...)` or `approve_saved_result(...)`.
- Reuse that already validated snapshot when building the successful response; do not reload it after the mutation.
- If snapshot validation fails, return the existing safe Stage 4 error before changing the review state.
- For legacy/unclassified jobs, preserve the existing Stage 3 save/approve behavior exactly and do not invent classifier data.
- Keep the snapshot digest and reviewed-HTML binding checks unchanged. Do not fall back to a later current classification.

Add focused Python/API tests proving that, for a classified job with a missing, malformed, digest-mismatched, or binding-mismatched snapshot:

- Save is rejected before any review revision/findings/approval state changes.
- Approve is rejected before approval state changes.
- A valid classified snapshot still appears in successful open/save/approve responses.
- Ordinary legacy Stage 3 save/approve remains unchanged.
