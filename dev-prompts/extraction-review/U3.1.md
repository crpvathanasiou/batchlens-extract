## Product scope

Build only this local MVP:

- The user selects a completed U2 lexical extraction job.
- The reviewed HTML is displayed one page at a time on the left.
- Findings for the selected page are displayed on the right.
- Findings are highlighted in the displayed HTML.
- Selecting a finding scrolls/focuses its evidence.
- The user can add, edit, and remove findings for the currently selected page only.
- The user can inspect all findings in a separate read-only “All findings” view. Selecting one navigates to its page; editing happens only in page view.
- The user saves the complete current result to the existing single-current-state JSON store.
- The user can use exactly one final action: `Approve extraction result`.
- Approval is only for the saved current extraction result. A later effective Save clears approval.

Do not build anything else.

## Explicit exclusions

Do not add:

- review history, revisions, version lists, approval ledgers, parent chains, deltas, retries, or SQLite;
- page, component, finding, automatic, or workflow approval;
- LLM, associations, graph work, PDF orchestration, new worker frameworks, or Stage 2 redesign;
- generic projection architecture, generic approval framework, pagination architecture, or new persistence layers;
- new documentation in `.ai/` or `AGENTS.md`.

Use the existing U1 current-state model and JSON store. Use the existing U2 completed job and raw L13 output as the source.

A document with 500–1,000 findings is normal for this MVP. It is acceptable to load the selected document’s current findings as one JSON payload.

## Backend

Follow the existing Stage 1 API and local-harness conventions. Keep the API surface small.

Implement only the endpoints/services needed to:

1. List completed U2 lexical jobs suitable for review.
2. Open one selected job:
   - read its reviewed HTML and its already-published Stage 2 lexical output;
   - if no current Stage 3 review JSON exists for that job, initialise the existing U1 current-state store once from the published lexical findings;
   - otherwise return the saved current state.
3. Save page-originated edits through the existing U1 transitions/store, using the current revision ID for stale-save conflict detection.
4. Approve the already-saved current result through the existing U1 approval transition.
5. Serve the reviewed HTML/page data required by the Vue UI.

Do not create a separate “projection subsystem”. Put the small, direct conversion from already-published lexical occurrences to existing U1 `ReviewFindingRecord` values next to the Stage 3 review service/API where it is used.

Reuse existing Stage 2/L13 readers and actual source fields. Preserve original matched text and source evidence. Do not invent spans, pages, block IDs, candidate IDs, or semantic relationships.

Every initial lexical finding must remain associated with its actual source page. A newly added finding belongs to the current page but has `no_document_evidence`; never invent a text span for it.

Keep the existing per-finding provenance semantics:

- original lexical text/evidence survive edits;
- added, changed, and removed provenance is retained;
- removal is a current-state tombstone/edit, not a rejection workflow.

Use the existing local actor convention from the project. Do not add authentication.

## Vue UI

Reuse the existing Vue application and styling patterns from Stage 1; do not create a second frontend application.

Create one simple Extraction Review Workspace screen:

- Job selector.
- Left panel: one reviewed HTML page at a time.
- Existing-style page navigation: dots, dropdown, and previous/next arrows.
- Right panel: findings for the selected page.
- A simple toggle:
  - **By page** — editable, only current page findings.
  - **All findings** — read-only overview. Selecting an item changes to that item’s page and returns to the editable page view.
- Add, edit, and remove controls appear only in **By page**.
- Save button.
- `Approve extraction result` button.
- Visible result status: `Not approved` or `Approved`.
- If there are unsaved edits, approval must not silently include them: require Save first.

Highlight lexical findings on the current page with transparent category-distinct styling for unit operations, materials, and equipment. Use non-colour information too, such as labels/list entries. A selected finding must visibly focus its evidence.

Use the existing Stage 2 evidence/page/block/span data and the reviewed HTML’s existing structure. Preserve its code-point offsets; do not solve or redesign browser UTF-16 offset handling in this task.

Do not add page approval markers, per-page checklists, or any implication that viewing a page means approval.
