## 1. Make the mutation context genuinely bounded

The current `ReviewTransitionContext` still accepts up to 5,000 `resolved_findings`, and initialization receives all findings. Save also fingerprints that complete collection.

This is not acceptable. U1.1 must not require loading, copying, or fingerprinting the whole extraction result merely to save a bounded edit batch.

Replace that design with the smallest explicit structure:

- Rename `resolved_findings` to a name that makes its limited purpose clear, such as `target_findings` or `resolved_edit_targets`.
- It contains only the existing findings addressed by the current `SaveReviewEditsCommand`.
- Its maximum length is `MAX_FINDING_EDITS_PER_SAVE`; remove `MAX_RESOLVED_FINDINGS`.
- It is a transient pure-transition input, never persisted history and never a complete current result.
- `InitializeReviewCommand` must not accept `initial_findings`.
- Initialization returns the head, immutable initialization revision, binding, and no loaded finding collection.
- A later caller supplies only the affected existing findings when requesting a save transition.
- Add operations require no existing target finding.
- Replace, patch-text, and remove operations require the matching supplied target finding.
- Reject missing, duplicate, unrelated, or extra supplied targets with a specific validation outcome.
- Return only the updated target findings for that same bounded mutation context.

Remove `resolved_findings_fingerprint()` and any whole-result comparison. Determine no-op behavior from the bounded requested edits and their supplied target values only.

A content-save revision must continue to contain only its bounded delta. No revision, transition context, command, or helper may retain or serialize the complete finding result.

## 2. Make the lexical-manifest SHA-256 mandatory at the Stage 3 boundary

Stage 3 must retain an exact lexical-manifest reference, including SHA-256. The current optional `PublishedManifestReference.manifest_sha256` and fallback manifest reference without a digest are insufficient.

Implement these rules:

- `PublishedManifestReference.manifest_sha256` is required.
- A completed `ExtractionRunReference` intended for Stage 3 review requires a `published_manifest` reference.
- Its `manifest_id` must match the Stage 2 final-manifest claim.
- The Stage 3 initialization transition rejects a completed publication that lacks the manifest SHA-256 reference.
- The immutable initialization revision retains that exact manifest identity and SHA-256 through its existing run binding or one direct, non-duplicated reference.
- Remove redundant duplicate raw-manifest fields if the same exact reference is already held by `ExtractionRunReference`. Prefer one authoritative manifest reference over two copies.
- The initialization fingerprint must include the manifest ID and manifest SHA-256.
- This contract records provenance only. It does not read files or verify the hash on disk; artifact verification remains a later task.

Keep `document_hash` distinct from the reviewed HTML byte SHA-256. The review binding must retain both the reviewed HTML identity and the lexical manifest SHA-256.

11. Existing R1 tests still prove immutable approval, edit-after-approval history, partial/zero-hit approval, provenance, explicit unassignment, stale conflict, and new-run isolation.
