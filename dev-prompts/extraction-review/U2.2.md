## Goal

Create one small local job service that:

1. accepts a U2.1 approved-document identity, one extraction action, and an existing L02 YAML configuration path;
2. runs Stage 2 in a local background thread;
3. persists truthful job status/progress so it can be queried after browser reload or service recreation;
4. registers the completed/failed run facts needed later to create an extraction-review state.

It must not create an API or UI.

## Supported actions

Reuse the existing `ExtractionReviewAction` mapping exactly:

- `extract_unit_operations` → `unit_operations_with_steps`
- `extract_materials` → `materials_with_quantities`
- `extract_equipment` → `equipment_with_parameters`
- `extract_all` → `full`

Each submitted local job executes one selected action. A user can later run other actions as separate jobs.

`fuzzy_enabled` is an explicit strict boolean job option and defaults to `False`.

A completed lexical run never auto-approves an extraction result and must not create or modify `current-review.json`.

## Concrete local layout

Under a caller-supplied `data_dir`, use only:

```text
<data-dir>/
  extraction-jobs/
    <local-job-id>.json
  extraction-raw-runs/
    <stage2-run-id>/
      ...existing L13 artifacts and final manifest...
```

- Each job JSON stores the latest state for that job. It is not a retry ledger or review-revision history.
- Stage 2 / L13 owns the raw run directory and artifacts.
- Do not add SQLite, a database, queue framework, event bus, generic repository layer, or job-history projection.

Use atomic JSON replacement for job-state writes.

## Required public model

Keep the job model compact and explicit. It must include enough persisted information to truthfully show:

- local job ID;
- approved-document identity (`job_id`, `review_revision_id`);
- requested `ExtractionReviewAction`;
- effective fuzzy flag;
- server timestamps for submitted/started/finished when applicable;
- lifecycle status: `queued`, `running`, `completed`, `failed`, or `interrupted`;
- truthful phase: `queued`, `validating_document`, `running_extraction`, `publishing`, `completed`, `failed`, or `interrupted`;
- validated `ReviewedHtmlV1Input` once document validation succeeds;
- Stage 2 run provenance and extraction outcome when produced;
- Stage 2 publication record;
- raw run directory relative to `extraction-raw-runs`, when one exists;
- final manifest ID and SHA-256 only when a final manifest exists;
- a safe structured error for terminal failure/interruption.

Do not invent percentages, total-work estimates, or per-page progress. Phase changes and final Stage 2 outcomes are the truthful progress for this first local worker.

A partial extraction with successful L13 publication is a completed job with its truthful partial component outcomes. A failed/interrupted publication is not completed.

## Service behavior

Add one small module under `src/app/extraction_review/`, for example `local_jobs.py`.

It must provide:

1. `submit(...)`
   - Persist `queued` state before returning.
   - Start one background `threading.Thread`.
   - Return the queued job immediately; never hold the caller until lexical work ends.
   - The submitted job receives:
     - approved-documents root;
     - `job_id` and `review_revision_id`;
     - L02 configuration path;
     - one `ExtractionReviewAction`;
     - optional `fuzzy_enabled=False`.

2. Worker execution
   - Move through the truthful phases above and persist each state transition.
   - Use `ApprovedDocumentsRegistry.select(...)` inside the worker.
   - Load the existing L02 config and override it only in memory:
     - selected reviewed HTML path;
     - selected preset;
     - no extra components;
     - selected fuzzy flag;
     - output directory `<data-dir>/extraction-raw-runs`.
   - Do not modify the YAML file.
   - Reuse the existing `run_lexical_extraction`, `FilesystemEvidenceSink`, and `finalize_publication`.
   - Hash the persisted final manifest bytes only after successful L13 publication and store that SHA-256 with the final manifest ID.
   - Convert expected selection/configuration/runner/publication failures into a safe terminal job error. Do not leak tracebacks or raw local paths in persisted error messages.

3. `get_job(local_job_id)`
   - Load and validate a persisted job JSON.
   - Return explicit not-found behavior for an unknown ID.

4. Reload/restart recovery
   - A new service instance using the same `data_dir` must load completed and failed jobs unchanged.
   - During service initialization, any persisted `queued` or `running` job left by a prior stopped process becomes terminal `interrupted` with a safe explicit interruption error. Do not attempt automatic resume or retry.

5. One worker per data directory
   - Use one simple in-process worker guard keyed by resolved `data_dir`.
   - A second active service for the same data directory must fail clearly rather than start a second writer/worker.
   - Keep this single-local-process mechanism small. Do not add cross-process locking infrastructure.

6. Testing support
   - Keep any test seam narrow and local. It may inject/monkeypatch the Stage 2 execution call, but production behavior must directly use the existing Stage 2/L13 implementation.
