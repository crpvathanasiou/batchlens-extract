## Deliverable and fixed rule

Add an optional `fuzzy_enabled` input, default `False`, at the existing callable dictionary matching boundary; arrange only the minimal additive plumbing required for the L10 parameter-name dictionary path to honor it when explicitly enabled. The later L12 runner will pass L02's effective `fuzzy_enabled` selection through this seam. There is still **one deterministic pipeline**; do not add a selectable algorithm, profile, edit threshold, field set, or method switch. When OFF, preserve the accepted exact/normalized-exact behavior and outputs. Do not modify L02's user-facing configuration schema.

Use the existing L05 `fuzzy_allowed` hint **and** the fixed V1 role/policy exclusions as eligibility gates. Fuzzy applies only to eligible, single, alphabetic natural-language words of at least six Unicode code points: equipment type, parameter name, unit operation, and independently eligible process step. Exclude Materials names/aliases and all chemicals, UNII/other identifiers, units, generic/context/support/inspection/step-cue terms, abbreviations, phrases, and equipment codes/models. Do not reinterpret source eligibility or introduce a language-filter subsystem. Ineligible terms remain available to exact/normalized-exact matching. A document word one character shorter than an eligible term must still be considered for a deletion match.

Use **ordinary Levenshtein distance 1** on the fixed L06 normalized comparison strings: one insertion, deletion, or substitution costs one; adjacent transposition alone costs two. Distance 0 remains exact or normalized-exact, never a fuzzy hit. Reject longer distances. Use L06 projection and default boundaries to produce the literal original block slice with zero-based, half-open Unicode code-point offsets; reject partial normalization units and invalid boundaries without silently misprojecting evidence. Keep the accepted L06 NFC scope, casefold, and boundary behavior; do not change normalization to improve fuzzy recall in L11. A fuzzy hit records `method="fuzzy"`, the original source term, `edit_distance=1`, and `rule_id="lexical-v1-fuzzy"` in the existing L01 evidence contract. It never rewrites document text or claims an entity association.

Extend `RawDiscovery` and the L08 spool/aggregation **only as necessary** to carry verified fuzzy distance into L01 `FuzzyEvidence`. L08 must validate the source row/term and eligibility and must not turn an arbitrary injected raw hit into a fuzzy claim; validate/recompute distance against the actual span using the same fixed comparison rule before creating evidence. Preserve deterministic aggregation: for one span and one source reference, `exact` outranks `normalized_exact`, which outranks `fuzzy`; retain all distinct eligible candidate interpretations and supporting row references. Exact evidence elsewhere in the block must not suppress an independent fuzzy occurrence. Preserve overlaps and repeated occurrences; do not impose top-1 or a hidden candidate cutoff.

Find fuzzy candidates using a **sound bounded index/filter** over the eligible terms in each existing L07 shard, followed by exact distance verification. A deletion-signature index is one possible simple design; choose a small implementation consistent with current code. Do not scan every document token against every catalogue term, build an all-vocabulary fuzzy index, or load the whole document. Account for index/signature memory as well as the existing shard's references, and fail explicitly on a finite bound rather than truncate matches. Keep replay identity pinning, early-close cleanup, per-block `result_buffer_records`, and stable discovery multisets across reasonable shard settings. ON adds fuzzy results without weakening exact search; OFF should not build fuzzy state. Fuzzy errors must map to bounded structured errors and must not claim completed coverage on failure.

**Resource clarification:** shard size comes from L02's explicit finite limits, not from querying host RAM. No hardware-adaptive shard sizing or privileged hardware access is required. Host RAM observations may be reported as optional diagnostics; L09's 32 GiB benchmark budget is not a runtime requirement.
